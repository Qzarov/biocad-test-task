# Roadmap to production

Что это за документ: честный список того, чего в решении нет, и в каком порядке это закрывать,
чтобы довести демо до боевого состояния. Разделено на техдолг, оставленный сознательно (я знал
и выбрал), пробелы (нужно, но не сделано), риски и порядок работ.

Оценки — в человеко-днях одного разработчика, для калибровки порядка, а не для плана-графика.

## 2. Чего не хватает для продакшена

**Наблюдаемость.** Сейчас есть только логи uvicorn. Нужно: структурные логи с `session_id` и
`request_id`, метрики (латентность хода, число tool_calls на ход, доля ходов с ошибкой
инструмента, стоимость токенов), трейсинг цепочки «запрос → LLM → MCP → SQLite», алерты на
рост ошибок 4xx/5xx от провайдера. Оценка 3–5 дней.

**Стоимость и лимиты LLM.** Ключ провайдера сейчас ничем не защищён от перерасхода: нет
лимита на пользователя, нет бюджета на сессию, нет учёта токенов. Нужны квоты, счётчик
стоимости на ход и мягкая деградация (переключение на более дешёвую модель) при исчерпании.
Оценка 2–3 дня.

**Безопасность.** Помимо аутентификации (1.5): валидация загружаемых файлов по размеру и типу
(сейчас ограничение только в nginx — 12 МБ), защита от zip-бомб в xlsx, CSP-заголовки,
секреты из vault вместо `.env`, аудит-лог всех правок плана с автором (человек или агент —
сейчас в метке снимка это видно, но без пользователя). Оценка 3–5 дней.

**Несколько планов в одном рабочем месте.** Сейчас всё — план, история снимков и переписка —
висит на `session_id`: один браузер = один план. Загрузка нового Excel заменяет план и стирает
переписку (старый разговор ссылался бы на задачи, которых больше нет), а держать две таблицы
рядом нельзя. Для боевого использования план должен стать сущностью первого класса:
`plan_id` в ключах вместо `session_id`, список планов с именем и файлом-источником, у каждого
своя история и своя переписка, переключалка в шапке, эндпоинты создания/переименования/удаления
и миграция существующих сессий в «план по умолчанию». Отдельно решить, что делать с
`GET /api/plan/template` и импортом: «загрузить как новый план» вместо «заменить текущий».
Оценка 5–8 дней; после аутентификации (1.5), потому что владелец плана — это уже пользователь.

**Многопользовательская работа над одним планом.** Сегодня сессия изолирована, и это скрывает
проблему: если двое откроют один план, последний пишущий победит. Нужны оптимистичные версии
снимков (при конфликте — «план изменился, обновите») и, в идеале, живые обновления по
WebSocket. Оценка 5–8 дней.

**Качество работы агента.** Нет офлайн-оценки: набор из 30–50 типовых запросов
(«перенеси всё после X», «выровняй загрузку», «сократи критический путь») с ожидаемыми
изменениями плана и метрикой «сколько запросов выполнено верно с первой попытки». Без этого
любая правка промпта или смена модели — прыжок в темноте. Оценка 3–5 дней, дальше — постоянно.

**Работа с большими планами.** Проверено на 12–17 задачах. На 500+ задачах упрётся: план целиком
уходит в системный промпт (нужна выжимка или выборочная подача через `get_plan` с фильтрами),
диаграмма рендерит все строки сразу (нужна виртуализация), снимок плана целиком на каждую
правку (нужны дельты). Оценка 5–8 дней.

**CI/CD.** Нет пайплайна: прогон pytest, сборка образов, скан зависимостей, автодеплой по тегу,
миграции стора. Оценка 2–3 дня.

**Функциональные пробелы, которые заметит PM.** Постоянные номера задач (сейчас номер — позиция
в списке и меняется при переупорядочивании; для ссылок в переписке нужен стабильный код вида
`T-12`); вехи (milestones) и группы задач; зависимости
не только finish-to-start; загрузка исполнителя и предупреждение о перегрузке; отпуска и
доступность; базовый план (baseline) и сравнение «план vs факт»; печать и экспорт в PDF;
i18n (интерфейс сейчас только на русском, строки в коде). Оценка 8–13 дней на весь список.

## 3. Риски

| Риск | Вероятность | Влияние | Что делать |
| --- | --- | --- | --- |
| Модель делает не то, что просили, и портит план массовой правкой | Средняя | Высокое | Есть undo и снимок на каждую правку. Дальше: предпросмотр «вот что изменится, применить?» для операций, затрагивающих больше N задач; аудит-лог с автором |
| Провайдер LLM недоступен или сменил формат tool-calling | Средняя | Среднее | Клиент уже абстрагирован до OpenAI-совместимого интерфейса — модель и endpoint меняются переменными окружения. Добавить фолбэк-провайдера и контрактный тест (1.8) |
| Расход токенов выходит из-под контроля | Средняя | Среднее | Квоты и учёт стоимости (раздел 2), лимит шагов уже есть |
| Пользователь загружает грязный Excel и не понимает, что не так | Высокая | Низкое | Импорт уже возвращает ошибки построчно. Дальше: предпросмотр разбора перед применением |
| Данные плана — коммерчески чувствительные, а уходят во внешний LLM | Средняя | Высокое | Обязательный пункт для боевого внедрения: либо self-hosted модель (endpoint уже конфигурируется), либо соглашение с провайдером и маскирование имён исполнителей |
| Потеря данных: SQLite-файл в томе без бэкапа | Средняя | Высокое | Переезд на PostgreSQL (1.4) + регулярные бэкапы и проверка восстановления |
| Библиотека диаграммы перестанет работать с новым React | Средняя | Среднее | Версии зафиксированы; план Б — свой рендер (1.7) |

## 4. Порядок закрытия

**Этап 1 — «можно показать заказчику» (1–2 недели).** Аутентификация (1.5), рабочий календарь
(1.1), структурные логи и метрики, CI с прогоном тестов, E2E-сценарий (1.9). Без этого нельзя
пускать даже пилот: либо не пустят по безопасности, либо не поверят датам.

**Этап 2 — «выдержит пилот на реальном проекте» (2–3 недели).** Несколько планов в одном
рабочем месте (иначе пилот упрётся сразу: у PM никогда не один проект), PostgreSQL (1.4),
пул MCP (1.2), квоты и учёт стоимости LLM, оптимистичные версии при одновременной работе,
офлайн-оценка качества агента.

**Этап 3 — «продукт» (3–4 недели).** Функциональные пробелы, которые ждёт PM (вехи, загрузка
ресурсов, baseline, PDF), большие планы (виртуализация, дельты, выборочная подача плана в
промпт), стриминг текста (1.6), i18n, решение по диаграмме (1.7).

Порядок именно такой: первый этап снимает блокеры внедрения, второй — операционные риски,
третий добавляет ценность. Пункты внутри этапа независимы и распараллеливаются.
